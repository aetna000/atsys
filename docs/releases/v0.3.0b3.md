# AtSys 0.3.0b3

Goal driven supervision, progress and durable final reports for general tasks.

## Install or upgrade

Python 3.10+ on macOS or Linux:

```sh
python -m pip install --upgrade atsys==0.3.0b3
cd /path/to/your/project
atsys init
```

Stable users can remain on 0.2.1. The wheel includes the backend, dashboard and
Codex skill; its dependency supplies Node 24. No npm or source checkout is needed.
Codex CLI and its existing authentication are required for Codex model-backed work.

For an existing installation, let active tasks finish or stop them explicitly
before replacing runtime files. Keep the same Python environment and
`ATSYS_DATA_DIR` to retain task history. Stop the owned dashboard and watchdog
before upgrading, then run `atsys service install` and `atsys ui` from the upgraded
environment. On macOS, unload the existing LaunchAgent with `launchctl bootout`
using its path shown by `atsys service status`; `service uninstall` deliberately
leaves a detached watchdog and is not an upgrade stop command. Do not remove the
old Python environment while its processes are running.

Refresh each project's managed skill with `atsys integrate` and reopen Codex.
Locally modified managed skills are preserved and require manual reconciliation.
An isolated virtual environment plus a separate `ATSYS_DATA_DIR` is recommended
for trying the beta alongside an existing service.

## What changed

- Goal intake records success criteria, deliverables, constraints, assumptions,
  unresolved decisions, ordered stages, observer rationale and recovery scope.
  The skill asks about material uncertainty and documents routine assumptions.
- New goal-contract submissions reject incomplete or unresolved contracts.
  Progress stays tied to declared stages and survives retries. Heartbeats and
  tool output alone do not count as progress.
- Every completed, blocked or stopped task automatically gets a durable local
  report, available in the dashboard, CLI and content-addressed storage.
  Reports include validation evidence, attempts, failures, limitations, available
  costs and the next action. Report generation makes no extra model/API call.
- Optional bounded structured outcomes distinguish completed work from passing
  domain results. Required missing or tampered outcomes cannot establish completion.
- Process cleanup rechecks ownership before signalling. Uncertain inspection
  cannot authorize killing a process; bounded reconciliation escalates with a
  concrete diagnostic instead of risking another task's runner.

```sh
atsys task report TASK_ID
atsys task report TASK_ID --json
# Explicit retrospective report for an older task; does not rerun it:
atsys task report TASK_ID --generate
```

## Compatibility and limits

Existing direct configurations without a goal contract remain supported and are
labelled legacy; this does not retroactively qualify their goals. Old receipts,
logs and frozen task settings are preserved. Optional worker outcome claims remain
worker-reported; validator-linked hashes identify the checked content, not the
truth of every claim. Unknown costs stay unknown. Workflow acceptance does not
mean every benchmark item passed or every domain objective succeeded.

This remains a single-operator beta. Commands run as the local user. Recovery is
bounded by explicit task policy, permissions, budgets and available tools; some
failures require human action. Generic goal intake depends on the installed skill
and declared evidence, not an independent semantic proof of the user's intent.
Linux needs a separately configured service manager for OS restart protection;
macOS has built-in LaunchAgent support. Windows supervision is unsupported.
Pause cannot suspend remote requests or provider timers.

See [goal workflow](../GOAL-WORKFLOW.md),
[implementation verification](../GOAL-WORKFLOW-VERIFICATION.md) and
[packaging](../PACKAGING.md). The historical verification describes a local b2
candidate; the b3 tag workflow separately rebuilds and tests the release artifacts
before PyPI publication. Its checks cover runtime tests, formatting, production
build, desktop/mobile browser behavior and clean installed-package tests, including
optional AtBot hooks without model calls. Local macOS packaging checks cover
LaunchAgent recovery; that check is skipped on Linux CI.
