# AtSys 0.4.0 release plan: interactive agent supervision

Status: planned; no implementation or release is claimed. Owner request: 7 November 2026.
Target: next feature release, provisionally 0.4.0. No package versions, installed
runtime, running services or provider settings change as part of this plan.

## User outcome

Start a visible Codex or Claude session through AtSys, give it an authorised task,
and leave routine work running. AtSys handles temporary provider failures and
low-impact choices without repeatedly interrupting the owner. The owner can
inspect the exact blocker, take control, pause or stop at any point. A closed
terminal or worker exit does not silently discard the task.

The three acceptance outcomes are:

1. An already-authorised routine operation does not repeatedly request approval.
2. A model-capacity failure or transient timeout leaves a recoverable task, with
   a visible next retry or approved model switch rather than an unexplained exit.
3. Naming and equivalent reversible implementation choices use recorded defaults.

## Verified starting point

Source baseline: main `69d11b3`; installed AtSys 0.3.3. Current provider probes:
Codex CLI 0.166.0 and Claude Code 2.1.281. These are qualification inputs, not
promises of compatibility with every future CLI release.

- `specs/009-model-capacity-recovery` already implements opt-in capacity detection,
  `capacityFallbackModels`, bounded recovery and model-selection receipts.
- That recovery starts a **fresh worker attempt**. It does not currently establish
  native provider session resume, interactive permissions or arbitrary terminal attachment.
- Native Claude workers currently use print/stream-json and noninteractive tool
  allowances. Native Codex execution is already structured. Reuse these adapters
  and the existing daemon/store/lease/validator rather than creating another scheduler.
- Claude's installed CLI advertises fallback models and host-mediated streaming
  permission requests; Codex advertises app-server and session resume. Probe the
  actual handshake/version before enabling any corresponding capability.
- The motivating Claude screenshot explicitly names an `ask` rule matching
  `Bash(rm -rf *)`. Broad permission does not establish an override of that rule.
  The download should use a new temporary directory when deleting an old one is
  unnecessary. Never silently weaken the owner's existing rules.

## Proposed operator interface

Proposed syntax, not commands shipped in 0.3.3:

```sh
atsys session start --provider codex --project /repo --policy /path/policy.json
atsys session start --provider claude --project /repo --policy /path/policy.json
atsys session attach SESSION_ID
atsys session status SESSION_ID
atsys session takeover SESSION_ID
atsys session stop SESSION_ID
```

Prefer an explicit session ID; never resume whichever session happens to be
`--last`. Persist the original objective and independent acceptance command when
known. An open-ended interactive session may report idle/turn-finished, but must
not report an objective completed without a declared validator.

A provider capability report must distinguish protocol-controlled execution,
terminal presentation, native resume, cross-model resume, approvals, question
responses and observation-only attachment. Starting through AtSys is the first
release path. Attaching to an arbitrary terminal started elsewhere is supported
only if a native attach protocol is qualified; otherwise report unsupported.

## Architecture and policy

The daemon retains execution ownership; the visible terminal is an attachable
view/input client. User input and takeover revoke automation's input lease so
AtSys cannot type at the same time as the owner. Keep at most one live worker
owner per session. Takeover does not itself grant new execution permissions.

Use structured provider events and native SDK/app-server permission interfaces
first. A PTY is a presentation/transport fallback only where required and tested;
never scan arbitrary output for the word "Yes" and press Enter. Unknown or
changed dialogs require attention. Do not treat model/tool output, retrieved text
or terminal escape sequences as authority to approve another operation.

A proposed schema-validated `sessionPolicy` is opt-in and separate from existing
task defaults. It records:

- Authorised project roots and action classes, explicit exclusions, policy revision
  and precedence; approvals are limited to the authority the owner supplied.
- Approved same-provider fallback models; provider/account switches require a
  separately configured handoff. Do not silently change subscription to paid API access.
- Retry count, maximum recovery elapsed time, backoff, optional provider retry hint
  and wait-after-exhaustion behaviour. Waiting is visible, durable and cancellable.
- Routine-decision defaults: naming convention, branch prefix and reuse of project
  conventions. Names must pass collision/path validation; no overwrite to force a default.
- Rules for uncertain effects, requiring reconciliation before replay.

Observers remain read-only, supervisors propose, deterministic policy authorises.
A model's "safe" classification cannot expand permission. Explicit provider/OS
restrictions remain effective; diagnose their source and report the exact conflict.
No runtime rule editing to bypass an unresolved approval. If the owner later
requests configuration changes, preview narrowly scoped changes and preserve originals.

## Permission and routine-decision behaviour

Normal authorised reads, edits, builds and tests may proceed through supported
policy interfaces. Evaluate the complete action and resolved targets, including
shell expansion, substitutions, symlinks and all compound commands. Do not approve
an opaque shell command merely because its prefix is allowed. Prefer simpler,
non-destructive commands where they fulfil the same authorised operation.

Permission decisions bind the session, provider request ID, exact action digest,
policy revision, scope and expiry. Repeated delivery returns the same receipt;
a changed command invalidates the decision. Store metadata/digests with redaction,
not secret-bearing raw commands or provider tokens. Every automatic response has
a reason the operator can inspect.

For user questions, apply defaults to low-impact names and equivalent reversible
choices, record the selected value, and continue via the native response interface.
Existing repository/skill requirements and owner instructions retain their
precedence. When an explicit requirement demands owner input, do not fabricate it.
Unknown budgets, credentials, data disclosure, destructive scope and externally
visible actions outside existing authorisation remain real blockers. Previously
approved releases/deployments do not need repeated generic confirmation, but their
specific repository/CI/publication gates still apply.

## Recovery and integrity

Persist provider session ID, task/attempt linkage, cwd, policy revision, last event
cursor, pending request, input ownership, selected model and recovery history.
Keep transcript references in provider-owned storage or access-restricted local
state; do not copy credentials into the journal.

Normalise capacity, transient transport/timeout, rate limiting, billing/quota,
authentication, permission, cancellation and unknown failures separately. Retry
transient failures with capped exponential backoff/jitter and provider Retry-After
when available. Never retry billing/auth failures as though they were capacity.
After same-model retries, choose only a configured accessible fallback and retain
the original model in the receipt. Exhaustion becomes a visible waiting/attention
state rather than completed; it must not run a hot retry loop indefinitely.

Resume the exact native session only when qualified. A provider/model boundary
that cannot resume needs an explicitly labelled checkpoint handoff carrying the
objective, approved policy, pending work and verifiable artifacts. Native history
is not assumed portable across providers. A fresh attempt is labelled as such.

A timeout is an uncertain outcome, not proof nothing happened. Reconcile writes,
Git operations, deployment IDs and external receipts before replay. Use stable
operation IDs where supported. If success cannot be established, pause that
operation for attention; keep the task/evidence intact. No exactly-once promise
for arbitrary shell or external tools.

Recognise legitimate provider waits/permission requests separately from a stalled
worker. Recovery waiting must not trip the activity observer repeatedly. Preserve
existing overall deadlines, attempts and budgets; define their accounting explicitly.
User cancellation stops owned process groups and prevents future retries; closing
a read-only view does not stop the daemon.

## Delivery sequence and implementation map

Before implementation, create a dedicated Spec Kit feature with an owner-supplied
feature directory, specification, research, plan, data model, interface contracts
and executable tasks. This document is release planning, not a replacement for
those required artifacts. Record the adapter capability spike before promising
interactive/native-resume support.

1. **Provider contract spike:** qualify Codex app-server and Claude host-mediated
   streaming with isolated synthetic sessions. Establish schema/version support,
   actual permission/question events, session IDs, cancellation and resume.
2. **Durable session and policy core:** extend `shared/operations.ts`,
   `shared/providers.ts`, `server/operations/config.ts` and store migrations;
   add session/policy modules under `server/operations/`. Keep legacy task behaviour.
3. **Recovery:** extend providers, attempt-runner and watchdog; add typed incidents,
   same-model delay, approved fallback, native resume/checkpoint handoff and fencing.
4. **Interactive control:** extend CLI, daemon/API and monitor with visible sessions,
   takeover, cancellation and policy-bound responses; add terminal adapters only
   for provider capabilities proven by the spike.
5. **Dashboard:** display session/attempt distinction, last verified progress,
   next retry time, current model, automatic decisions, exact blocker and takeover.
   Do not equate heartbeat or an open terminal with successful work.
6. **Qualification and release:** run the matrix below, document limits and migration,
   synchronise actual package constants at release time, build/install artifacts,
   and complete the repository's publication and website handoffs.

## Release acceptance matrix

Use isolated stores/workspaces and synthetic tools. Fixtures test deterministic
control-plane transitions; small real-provider canaries separately qualify actual
invocation, permission and resume semantics. Record versions, account surface,
result, resource use and untested capabilities. Do not rerun production benchmarks
or spend on a long soak without explicit bounds.

| Scenario | Required evidence |
| --- | --- |
| Capacity response | Saved task survives; visible delay; bounded same-model retries then approved fallback |
| All fallback models unavailable | Durable waiting/attention, no busy loop, no false completion |
| Mid-turn timeout after a write | Reconciled result; no duplicate write or unapproved replay |
| Authentication/billing/permission failure | Correct classification; no capacity loop or permission bypass |
| Routine naming question | Valid collision-free default, durable reason, continued work |
| Known authorised permission request | Correct exact request answered once via supported interface |
| Changed/expired/replayed request | No stale approval or duplicated operation |
| Screenshot-style compound cleanup | New temp directory where appropriate; no broad rm approval |
| Spoofed output or injected Yes prompt | No approval/input generated from untrusted text |
| Daemon crash during retry/approval | Journal restored, one owner, receipt/state preserved |
| Provider session resume | Same exact ID and history verified; otherwise explicit unsupported/handoff |
| Terminal closes, reconnects, owner takes over | Daemon continues; input ownership prevents competing responses |
| Stop during wait or request | Owned processes stopped and no delayed restart |
| Existing supervised tasks | Validators, hooks, scopes, artifacts and reports unchanged |
| Clean upgrade/reinstall | Backward-compatible migration; no source/hooks/credentials overwritten |

Required gates: `npm test`, `npm run typecheck`, `npm run build`, relevant Playwright
checks, installed Python artifact tests, and bounded real Codex/Claude canaries on
macOS and Linux. Dashboard checked at desktop/mobile sizes. Windows supervision
remains unsupported unless separately implemented and qualified; do not advertise
it from CLI presence or mock fixtures. Unknown model costs remain unknown and
live tests need explicit count/time bounds.

## Release completion and constitution check

All five constitutional principles apply: local-only by default, durable authority,
verified outcomes, capability-labelled provider independence and tested increments.
The existing runtime/service must not be upgraded underneath unrelated active tasks.
New automation is opt-in; upgrades do not expand old tasks' authority.

0.4.0 may ship only with the three user outcomes measured for both Codex and
Claude on the supported paths. If a native provider protocol cannot expose a
required interaction, record the blocker and revisit scope/version; do not ship a
screen-scraping substitute under the same promise. Native session resume, model
switching and process liveness must remain distinct in docs and UI.

Publish accurate install/upgrade instructions, permission defaults, capability
matrix, recovery limits, privacy/log retention, manual takeover and uninstall
instructions. Verify package publication separately from the AtMem.ai website
PR and live deployment. This plan authorises none of those publications itself.
