# Delegate work through AtSys

AtSys is installed as the `atsys` command. You prepare the task; its managed worker owns execution. The package supplies the schema, defaults, runtime and dashboard; no source checkout is needed.

If `ATSYS_TASK_ID` is set, or your prompt identifies you as an AtSys worker, supervisor or repair agent, perform that assigned role directly. Do not create a nested AtSys task.

For a new objective:

1. Extract goal, deliverables, measurable success criteria and constraints from the request plus relevant project instructions and inspection. Record routine assumptions. Ask concise questions only for material unanswered choices (ambiguous acceptance, destructive/external scope, or unknown budgets needed for execution). Continue independent inspection/planning while awaiting answers; launch dependent work only when resolved. Preserve unrelated work. Read [task configuration](references/task-config.md) for the contract and interface.
2. Create a configuration using `atsys task template --worker copilot --objective "..." --output .atsys/tasks/<name>.json`. Complete goalContract with successCriteria, deliverables, constraints, assumptions, unresolvedDecisions, ordered stages, planSource, observers with cadenceSeconds and rationale, recoveryScope, escalationConditions and budget. Leave material unanswered questions in unresolvedDecisions; submission is guarded until resolved. Set a real execution plan, project directory and declared acceptance command. Select progress observation for meaningful stages/work units, activity only when silence indicates trouble, and heartbeat for runner liveness. Justify each configured hook with a matching observer hookId, bounds and rationale; do not install arbitrary hooks. Use independent validation and requiredArtifacts for deliverable digests. Unknown costs stay unknown; record limits without inventing prices. Use the GitHub Copilot worker and current configured model unless the user specifies a model. Set supervised recovery with two retries and bounded deadlines. Enable bounded repair only within the work the user authorized; automatic repair does not authorize unrelated edits or external actions.
3. Run `atsys doctor --config <file>` for setup/executable/write-pilot checks. Resolve failures within scope; never invent acceptance criteria or read credentials. New GitHub Copilot tasks receive unique goal-progress monitoring by default; do not disable it for convenience. Authorize `networkAccess` explicitly when the user's task requires network access; this does not broaden spending or external-write authority. Use `atsys service status` and ensure watchdog protection is healthy (`atsys service install` on macOS when needed). Submit exactly once with `atsys task submit --config <file>`. Preserve the returned task ID; if submission output is lost, inspect `atsys task list` before considering another submission.
4. Use `atsys task show <id>` to confirm an attempt has started and its heartbeat is recent. Report the ID, objective, acceptance criteria, recovery limits and dashboard link from `atsys ui --no-open`. If startup fails, report the actual state/error rather than claiming a successful handoff.

When the objective needs project-specific progress checks or agent tool/turn callbacks, read [hook configuration](references/hooks.md). Keep default GitHub Copilot milestone monitoring unless replacing it with a real custom progress source; hook activity alone is not progress.

For an existing task, inspect its state before changing it. `atsys task stop <id>` and `atsys task retry <id>` persist operator intent; configuration changes can be made in the dashboard. Report whether a task is running, validating, recovering, completed, stopped or needs attention based on persisted evidence. A model's success statement is not completion evidence.

For the operator's terminal, prefer `atsys task status <id>` and `atsys task watch <id>`; `atsys task logs <id>` formats activity from all attempts, newest first, and filters nested provider/tool envelopes. The dashboard activity panel supports attempt/text filters and pausing display independently of execution. Do not dump full task JSON or tool transcripts as a progress update. `task show` remains the complete machine inspection interface. Closing the read-only watch does not stop the task.

Track goal stages through the configured progress source, preserving evidence and retry checkpoints. Worker exit and full progress are not acceptance. Recover only within authorized scope and bounded attempts; reconcile uncertain effects before retry. Inspect `atsys task report <id>` at terminal state. AtSys automatically creates a local report for completed, blocked/failed (needs_attention), and stopped tasks. Report failure is visible and prevents a completion claim. Reports separate declared-validator acceptance from worker-reported domain outcomes; preserve partial failures. Legacy attachment uses explicit `atsys task report <id> --generate [--outcome-file relative.json]`; never rerun work or rewrite receipts to make a report. Do not infer domain success from completed status.

Copilot/Claude worker and repair shell tools require explicit trustedLocalExecution:true (template --trusted-local-execution) within the user-authorized local coding scope. Never imply this is Codex sandbox containment or an OS network denial. Preserve this constraint in the goal contract; if incompatible, select Codex rather than weakening it. Supervisor and repair providers may be selected independently.
