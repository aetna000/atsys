# Goal driven autonomous task workflow

Owner request, 2026-10-26: AtSys must manage general tasks from intent to a conclusive outcome without the owner interpreting logs or directing routine repairs. This applies to coding, research, operations and benchmarks; no benchmark-specific domain model.

## Requirements

1. Intake extracts a concrete goal, deliverables, acceptance evidence, constraints and unresolved decisions from the request plus project inspection. Routine implementation choices use documented assumptions; materially ambiguous goals, destructive/external actions or unknown budgets trigger concise clarification before dependent execution. Do not treat a vague request as a qualified launch. The installed AtSys skill and task templates must teach and enforce this workflow where machine-verifiable.
2. A reviewable goal contract and ordered plan record success criteria, the verification method, progress stages/signals, observer cadence and rationale, recovery scope, escalation conditions, budgets/limitations and final-report deliverables. Consult the user on consequential unresolved choices, not routine steps. No arbitrary hooks or provider changes without task authority.
3. Execute autonomously with durable progress tied to the task's own goal. Task stages and work-item counts remain distinct from heartbeat, tool traffic, pass/fail counts and acceptance. Use progress files and bounded hooks when justified by the plan. No invented percentages, default denominators, successful work or resolved questions. Progress survives retries; stalled progress causes bounded investigation/recovery rather than silent waiting.
4. The console and CLI prioritize goal, success criteria, current goal stage, evidence-based progress, blocker/recovery and next action. Logs preserve progress and final outcome. Domain-specific totals are optional structured task outcomes, not hard-coded benchmark policy.
5. Every terminal transition generates a durable, readable final/blocked/stopped report automatically, with task identity/goal, work and attempts, verified outcome, acceptance evidence/artifact digests, remaining failures/limitations, available costs (unknown stays unknown), and next action. Worker exit zero or 100% reported progress does not establish goal acceptance. Report generation is local/deterministic and uses no extra judge/API.
6. Domain outcome reports supplied by workers can enrich the report through an explicit bounded, validated and redacted contract. Their claims remain worker-reported unless linked to validator evidence. Task completion requires its declared validation; missing/tampered required outcome evidence cannot be marked complete. Existing completed tasks may get clearly labelled retrospective summaries without rerunning work or rewriting original receipts.
7. Reports are available in the dashboard, CLI and durable storage after context/cache loss. Task outcomes distinguish workflow acceptance from domain results (e.g. completed items versus passing items) and retain failures. No silent promotion, rerolls or automatic new scope.
8. Backward compatibility: old tasks/configs remain readable. New intake requirements do not invalidate original run identity or rewrite frozen task/benchmark settings. Preserve existing progress-renderer fixes and unrelated work. No changes to private benchmark evidence or any new benchmark/model run.

## Acceptance

Real command tasks cover success with partial domain results, validator failure, missing evidence, retry/repair, stopped and blocked outcomes. Reopen persisted state and verify report identity/digest, deterministic/idempotent generation and redaction. Test generic goal intake/clarification gates and hooks/progress rationale. CLI and desktop/mobile goal/progress/final-report views must be verified with isolated service state. Existing suites, typecheck and build must pass. No paid models in tests.
